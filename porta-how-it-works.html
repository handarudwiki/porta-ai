The end-to-end loop

From headline to alert in one pass

  • 1 · Trigger — dashboard load, a manual "Poll" click, or an hourly Vercel cron all hit GET /api/poll.
  • 2 · Ingest — fetchSectorsNews() returns live news or the sample dataset (9 articles).
  • 3 · Dedupe — existing events load from Postgres; already-sent IDs seed an in-memory set.
  • 4 · Extract — each new article → extractEventFromNewsDynamic() → a Universal Event Envelope.
  • 5 · Score — evaluatePortfolioImpact() computes sentiment, exposure %, and IDR impact per holding.
  • 6 · Persist — saveArticlesAndEvents() idempotently upserts everything.
  • 7 · Alert — HIGH relevance or materiality ≥ 0.85 → Telegram flash alert, then marked sent.
  • 8 · Surface — events render as cards; each links to a detail page with flowchart + simulator.
The hub · app/api/poll/route.ts

The poll route ties it all together

One function, processArticlesAndEvents(), orchestrates fetch → extract → persist → alert.

// 1. Fetch news (live Sectors API, or sample fallback)
const articles = await fetchSectorsNews();

// 2. Load existing events → skip re-extracting, seed sent-set
const dbEvents = await getPersistedEvents();

// 3. Extract each new article concurrently (Gemini or fallback)
const events = await Promise.all(articles.map(extractEventFromNewsDynamic));

// 4. Persist articles + events (idempotent upsert)
await saveArticlesAndEvents(events, articles);

// 5. Auto-alert the high-impact ones
if (relevance === "HIGH" || materiality >= 0.85) sendTelegramNotification(evt);
GET auto-sends when ?autoSendTelegram=true, the Vercel cron header is present, or a valid CRON_SECRET is passed. POST accepts manual creds in the body.
The brain · lib/event-extractor.ts

The 5-layer extraction pipeline

Layer 1

Detection

Classify into 1 of 9 categories & ~40 event types.

Layer 2

Extraction

Pull structured metrics into a flexible event_data payload.

Layer 3

Normalization

Entities, affected sectors & companies, transmission steps.

Layer 4

Impact analysis

Materiality score + market impact level.

Layer 5

Portfolio relevance

Handed to the portfolio engine for exposure scoring.

Resilience

Gemini + Fallback

Gemini 2.5 Flash with a schema-constrained response. If the key is missing or the call fails, a deterministic keyword extractor takes over — silently.

The contract · types/event.ts

One shape to rule them all

Rather than 9 tables for 9 categories, every event becomes a single Universal Event Envelope — fixed columns for shared fields, one flexible JSON payload for the rest.

interface UniversalEventEnvelope {
  event_id, category, event_type, title, summary
  entities:            EntityRef[]
  event_data:          Record<string, any>   // per-type metrics
  factuality:          { status, confidence }
  market_impact:       { materiality, level }
  affected:            { sectors[], companies[] }
  economic_mechanism:  TransmissionStep[]     // the causal chain
  portfolio_impact:    PortfolioImpactSummary // $ effect on you
  telegram_sent, telegram_sent_at
}
Stored across two tables: articles (raw news) and events (with jsonb columns for the nested structures).
The engine · lib/portfolio.ts

Scoring the event against you

evaluatePortfolioImpact() loops each holding, decides if it's hit by ticker or sector, then applies category-specific heuristics.

Example rules

Rate hikeBanks & Property → bearish
Export-tax upNickel miners (INCO, ANTM) → bearish
Commodity moveMining scales with price %
Earnings beatCompany → bullish
DividendComputes actual cash flow

Outputs per event

exposure % net est. % impact net IDR impact BULLISH BEARISH relevance: HIGH / MED / LOW

Relevance is HIGH when exposure ≥ 30% or |net %| ≥ 1.0. That threshold is exactly what decides whether a Telegram alert fires.

The portfolio is a hardcoded 7-position demo baseline (BBCA, BMRI, INCO, ANTM, ASII, CTRA, Cash) — no auth/user accounts.
The alert · lib/telegram.ts

The Telegram flash alert

What triggers it

  • Auto — the poll route fires for HIGH-relevance / high-materiality events.
  • Manual — any event can be sent from the UI via POST /api/telegram.
  • Dedupe — an in-memory set + a durable telegram_sent DB flag prevent repeats.
  • Simulation — with no bot creds it returns a simulated result instead of failing.

Optional everywhere, graceful always

GEMINI_API_KEY→ else keyword fallback

TELEGRAM_*→ else simulation mode

Automation

vercel.json schedules the poll hourly:

"crons": [{
  "path": "/api/poll?autoSendTelegram=true",
  "schedule": "0 * * * *"
}]

So Porta keeps working — and alerting — with no one watching the screen.

Trade-off worth noting: failures are quiet (logged as warnings), which is great for demos but hides errors in production.
